## 1. 教学目标 (Learning Objectives)

*   **协议选型**: 理解 MQTT 在低带宽、不稳定网络环境下的工程优势（相对于 HTTP/Modbus）。
*   **版本决策**: 掌握 MQTT 3.1.1 与 5.0 的核心差异，能够根据项目需求选择合适的版本。
*   **Topic设计**: 学会设计层级清晰、权限可控的主题命名空间（Topic Namespace）。
*   **QoS机制**: 深入理解 QoS 0/1/2 的重传机制与性能开销，做出正确的工程权衡。
*   **高级特性**: 熟练运用 保留消息 (Retained) 和 遗嘱消息 (LWT) 解决设备状态同步问题。

## 2. 规范与标准依据 (Standards & Regulations)

| 标准编号 | 标准名称 | 关键特性 | 适用场景 |
| :--- | :--- | :--- | :--- |
| **ISO/IEC 20922:2016** | MQTT v3.1.1 | 极简、二进制头部、发布/订阅模式。 | 存量设备、资源极度受限的 MCU（如 8-bit/16-bit）。 |
| **OASIS MQTT v5.0** | MQTT v5.0 | 增加会话过期间隔、原因码、用户属性、共享订阅。 | 现代 IoT 平台、大规模并发、微服务架构集成。 |

## 3. MQTT v3.1.1 vs v5.0 工程选型 (Engineering Selection)

| 特性维度 | MQTT v3.1.1 (经典版) | MQTT v5.0 (增强版) | 工程价值 |
| :--- | :--- | :--- | :--- |
| **错误反馈** | 仅连接断开，无具体原因 | **原因码 (Reason Codes)** | 5.0 能区分“鉴权失败”与“服务器忙”，极大降低调试难度。 |
| **元数据** | 不支持自定义头部 | **用户属性 (User Properties)** | 5.0 可在头部携带 TraceID、设备类型等，**无需解析 Payload** 即可路由。 |
| **负载均衡** | 不支持 (需应用层实现) | **共享订阅 (Shared Subscriptions)** | `$share/group/topic`，支持服务端自动负载均衡，适合后端微服务集群消费。 |
| **会话管理** | `Clean Session` (0/1) | `Clean Start` + `Session Expiry` | 5.0 允许设备断线后保留会话（如1小时），且连接时可选择是否清除旧会话，更灵活。 |
| **性能控制** | 无 | **流量控制 (Flow Control)** | 5.0 支持限制未确认消息数量，防止慢客户端被消息积压冲垮。 |

> **[工程建议]**: 对于新项目，**强烈推荐使用 MQTT 5.0**。除非受限于旧硬件的 SDK 支持（如老旧 PLC 仅支持 3.1.1）。

## 4. 关键设计模式 (Design Patterns)

### 4.1 主题命名空间设计 (Topic Namespace)
好的 Topic 设计应具备：可读性、权限隔离性、可扩展性。
*   **反例**: `data`, `sensor/temp`, `device1` (含义不明，无法鉴权)
*   **推荐格式**: `root/location/device_id/message_type`
    *   `sys/factory_a/line_2/machine_05/telemetry` (遥测数据)
    *   `sys/factory_a/line_2/machine_05/alert` (报警数据)
    *   `cmd/factory_a/line_2/machine_05/set_speed` (下行指令)
*   **工程原则**:
    *   **不要**在 Topic 中包含易变信息（如数值）。
    *   **权限控制**: ACL 规则可配置为 `sys/factory_a/#`，方便按区域授权。

### 4.2 QoS 等级权衡 (Quality of Service)
*   **QoS 0 (At most once)**: "发后即忘"。
    *   **适用**: 高频传感器数据（如 10Hz 振动），丢几个包不影响趋势分析。**带宽占用最小**。
*   **QoS 1 (At least once)**: "至少一次"。
    *   **适用**: 关键状态（开关机）、报警信息。**工程中最常用**。需应用层处理“重复消息”去重（幂等性）。
*   **QoS 2 (Exactly once)**: "恰好一次"。
    *   **适用**: 计费数据、金融交易。**开销极大**（4次握手），极大降低吞吐量，慎用。

### 4.3 状态同步机制 (State Synchronization)
*   **保留消息 (Retained Messages)**:
    *   **场景**: App 打开时需要立即知道设备当前状态（无需等待下一次上报）。
    *   **做法**: 设备发布状态时标记 `Retained=true`，Broker 会缓存最新一条。新订阅者连上即收。
*   **遗嘱消息 (Last Will & Testament - LWT)**:
    *   **场景**: 检测设备**非正常断线**（断电、断网）。
    *   **做法**: 连接时预设 LWT（Topic: `status`, Payload: `offline`）。若心跳超时，Broker 自动代发此消息。

## 5. 常见坑点与排查 (Troubleshooting)

### 5.1 "Keep Alive" 误区
*   **现象**: 设备频繁掉线重连。
*   **原因**: 心跳间隔设置过短（如 60s），但网络抖动或 NAT 超时（运营商通常几分钟关闭空闲 UDP/TCP 链接）。
*   **对策**: 建议 Keep Alive 设为 60s~120s，并在应用层开启 TCP Keepalive 探测。

### 5.2 Client ID 冲突
*   **现象**: 两台设备交替掉线（踢皮球）。
*   **原因**: 使用了相同的 `Client ID`。MQTT Broker 规定同一时刻 Client ID 必须唯一，新连接会踢掉旧连接。
*   **对策**: Client ID = `ProductKey` + `DeviceSN` (确保全局唯一)。

### 5.3 消息积压
*   **现象**: 订阅端刚连上，瞬间收到大量旧消息，导致 CPU 飙升或内存溢出。
*   **原因**: 使用了 `Clean Session=false` (3.1.1) 且 QoS>0，Broker 缓存了离线期间的所有消息。
*   **对策**:
    *   对于非关键数据，使用 QoS 0。
    *   MQTT 5.0 设置 `Message Expiry Interval`（消息过期时间），避免缓存太久的数据。

## 6. 思考题 (Practice)

1.  **Q**: 为什么不建议在 MQTT Payload 中传输高清图片或视频？
    *   **A**: MQTT 是为短消息设计的，大文件会长时间占用单线程处理资源，阻塞心跳包发送导致掉线。大文件应传 **URL**，通过 HTTP/FTP 另行下载。
2.  **Q**: 什么时候应该使用 MQTT over WebSocket？
    *   **A**: 当客户端是 **Web 浏览器**（如监控大屏 Dashboard）或 小程序时，因为浏览器无法直接建立原生 TCP 连接。
