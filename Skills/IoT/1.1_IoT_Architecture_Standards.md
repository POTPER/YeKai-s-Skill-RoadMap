## 1. 教学目标 (Learning Objectives)

*   **架构认知**: 理解 ISO/IEC 30141 与 IEEE 2413 定义的标准参考架构。
*   **分层设计**: 掌握感知识别层、网络构建层、平台管理层、综合应用层的工程边界与职责。
*   **关键决策**: 能够根据时延、带宽、功耗等约束条件，进行“边缘计算 vs 云端计算”的架构选型。
*   **标准化思维**: 建立基于国际标准（ISO/IEC, IEEE）的系统设计思维，避免“烟囱式”开发。

## 2. 规范与标准依据 (Standards & Regulations)

> **[重要]** 架构设计应遵循以下国际标准，以确保系统的互操作性与可扩展性。

| 标准编号 | 标准名称 | 关键内容 | 工程应用 |
| :--- | :--- | :--- | :--- |
| **ISO/IEC 30141** | Internet of Things (IoT) — Reference Architecture | **六域模型**: 用户域、目标对象域、感知控制域、服务提供域、运维管控域、资源交换域。 | 提供了通用的词汇表和架构视图，用于统一多方沟通语言。 |
| **IEEE 2413-2019** | Standard for an Architectural Framework for the IoT | **三层架构**: 设备层、网络/边缘层、云/应用层。 | 强调跨领域的互操作性（如智慧城市与智能交通的数据共享）。 |
| **ITU-T Y.2060** | Overview of the Internet of Things | **四层模型**: 设备层、网络层、服务支持层、应用层。 | 电信级物联网系统的基础参考模型。 |

## 3. 工程架构分层详解 (Layered Architecture)

从工程落地角度，通常采用经典的 **“端-边-管-云”** 四层架构：

### 3.1 感知识别层 (Perception / Device Layer)
*   **核心职责**: 数据采集与执行控制。
*   **关键组件**:
    *   **传感器 (Sensors)**: 温湿度、加速度、气体浓度等（模拟量/数字量）。
    *   **执行器 (Actuators)**: 继电器、伺服电机、阀门。
    *   **控制器 (MCU/PLC)**: STM32, ESP32, Siemens S7-1200。
*   **工程约束**:
    *   **功耗**: 电池供电设备需采用低功耗设计（如休眠策略）。
    *   **环境**: 工业级宽温（-40℃~85℃）、IP67防护、防爆等级。

### 3.2 网络构建层 (Network / Transport Layer)
*   **核心职责**: 数据的可靠传输与接入。
*   **通信技术选型**:
    *   **短距无线**: BLE 5.0 (低功耗, <50m), ZigBee 3.0 (自组网, <100m), Wi-Fi 6 (高带宽)。
    *   **广域无线 (LPWAN)**: NB-IoT (运营商基站, 深度覆盖), LoRaWAN (私有部署, 长距离)。
    *   **有线工业总线**: RS-485 (Modbus RTU), EtherCAT, PROFINET。
*   **工程考量**: 信号覆盖盲区、频谱干扰、丢包重传机制。

### 3.3 边缘计算层 (Edge Computing Layer) —— **架构关键点**
*   **位置**: 网关 (Gateway) 或 本地服务器。
*   **核心职责**:
    *   **协议转换**: 将 Modbus/OPC UA 转换为 MQTT/HTTP。
    *   **数据清洗**: 过滤噪声数据，聚合高频数据（如 100Hz -> 1Hz）。
    *   **实时控制**: <10ms 的本地逻辑闭环（断网也能运行）。
*   **标准参考**: **IEEE 2413** 强调了边缘层在降低云端负载和提升隐私保护中的作用。

### 3.4 平台管理层 (Platform / Cloud Layer)
*   **核心职责**: 设备管理、数据存储、大数据分析。
*   **关键模块**:
    *   **设备影子 (Device Shadow)**: 缓存设备状态，实现异步控制。
    *   **规则引擎 (Rule Engine)**: 基于 SQL 的消息路由与联动。
    *   **OTA (Over-the-Air)**: 固件远程升级管理。

## 4. 架构决策模型 (Decision Framework)

在设计系统时，需根据业务需求进行 **“边缘 vs 云端”** 的算力分配决策：

| 决策维度 | 倾向于 **边缘计算 (Edge)** | 倾向于 **云端计算 (Cloud)** |
| :--- | :--- | :--- |
| **时延要求** | **极低** (<20ms)<br>例如：自动驾驶、工业机械臂防碰撞 | **一般** (>200ms)<br>例如：环境监测 dashboard、历史报表 |
| **带宽成本** | **高** (视频流/高频振动数据)<br>需本地预处理，只传特征值 | **低** (温湿度/状态量)<br>直接透传原始数据 |
| **数据隐私** | **敏感** (人脸/医疗数据)<br>本地脱敏后上传 | **公开/非敏感**<br>全量上传备份 |
| **断网容忍** | **不可容忍**<br>断网必须保持基本控制功能 | **可容忍**<br>断网仅影响远程查看 |

## 5. 常见架构模式 (Patterns)

### 5.1 直连模式 (Direct Connection)
*   **拓扑**: 设备 (4G/Wi-Fi) -> 云平台。
*   **适用**: 消费类电子（智能插座）、独立气象站。
*   **优点**: 架构简单，成本低。
*   **缺点**: 依赖外网，设备功耗较高。

### 5.2 网关模式 (Gateway Pattern)
*   **拓扑**: 子设备 (ZigBee/485) -> 边缘网关 -> 云平台。
*   **适用**: 智能家居、工厂产线监控。
*   **优点**: 支持异构协议，边缘自治，节省公网流量。
*   **缺点**: 网关是单点故障风险（需考虑双机热备）。

## 6. 思考与实战 (Review & Practice)

### 6.1 工程师自检清单
1.  [ ] **协议标准化**: 系统内部是否尽量统一了通信协议（如统一转为 MQTT）？
2.  [ ] **心跳保活**: 是否设计了合理的心跳包机制，既能及时发现离线又不浪费流量？
3.  [ ] **安全认证**: 设备接入是否强制使用了双向认证（mTLS）或 Token 机制？
4.  [ ] **数据缓存**: 网关断网时，是否具备断点续传功能（Local Storage）？

### 6.2 案例思考
**场景**: 一个地下停车场的 CO 浓度监测与排风扇联动系统。
*   **Q**: 应该选择直连模式还是网关模式？联动逻辑放在云端还是边缘？
*   **A (建议)**:
    *   **模式**: **网关模式**。地下信号差，通过有线/LoRa 汇聚到网关更可靠。
    *   **逻辑**: **边缘侧**。CO 超标危及生命，必须保证断网时风扇仍能立即启动（本地 PLC/网关逻辑），云端仅作为状态记录和远程报警。
