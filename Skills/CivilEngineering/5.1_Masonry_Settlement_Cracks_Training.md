# 5.1 实训任务：砖混结构沉降裂缝鉴定 (Masonry Settlement Cracks Training)

> **场景类型**: Agent-Based Learning (ABL) 交互式实训
> **难度等级**: ⭐⭐⭐ (Advanced)
> **参考规范**: JGJ 125-2016, JGJ 8-2016

## 1. 实训任务书 (Mission Brief)

**背景**: 你是“建科院”的一名高级工程师。城区某老旧砖混住宅小区（建于1998年）近期出现多处墙体裂缝，居民投诉剧烈，怀疑与隔壁新建大楼的基坑施工有关。

**你的任务**: 由于你分身乏术，你需要训练一个 **AI 助手 (Agent)** 代替你去现场进行初步勘查和鉴定。你需要教会它“看什么”（收集线索）、“怎么判”（注入规则）以及“怎么测”（调试工具）。

**最终目标**: Agent 能够独立输出一份符合 JGJ 125 标准的《房屋危险性初步鉴定报告》。

## 3. Phase 1: 现场踏勘与上下文构建 (Field Inspection & Context Building)

### 3.1 本场景的 Agent 认知逻辑 (Cognitive Logic for This Scenario)

虽然 Agent 的学习框架是通用的，但在 **“沉降裂缝”** 这一特定任务中，Agent 面临独特的认知挑战。本阶段的目标是建立针对本病害的 **“领域认知模型”**。

*   **感知难点 (The Perception Challenge)**: 
    *   **几何形态的受力隐喻**: Agent 容易把裂缝看作简单的“线条”。你需要教会它识别 **“倒八字” (上宽下窄)** 这一特征，因为它直接对应了 **“剪切破坏”** 的力学模型。如果 Agent 无法区分“正/倒八字”，它就无法反推地基的沉降形态（中间沉 vs 两端沉）。
*   **上下文依赖 (Context Dependency)**: 
    *   **环境即因果**: 在本案中，**“深基坑”** 是推理链条中缺失的拼图。如果不将“基坑降水”这一环境信息注入 Context，Agent 几乎必然会根据训练数据中的先验概率，将裂缝误判为更常见的 **“温度收缩裂缝”**。
*   **特定的幻觉陷阱 (Specific Hallucination Trap)**: 
    *   **归因谬误**: 当缺少“地基位移”证据时，Agent 倾向于“向内归因”，编造出“砖块强度不足”或“砂浆老化”等内部原因。这在工程鉴定中是致命的错误（方向性误判）。

**你的角色**: 你不仅是观察者，更是 **“上下文架构师”**。你需要通过采集特定线索，强行纠正 Agent 的这种潜在偏见。

### 3.2 场景环境 (The Environment)
*   **主体建筑**: 6层砖混结构住宅，条形基础。
*   **周边环境**: 东侧 15米处有一个正在施工的深基坑（已开挖至-10m）；西侧为绿化带。
*   **操作模式**:
    *   **无人机模式 (Drone View)**: 模拟 `Global Perception`，建立宏观空间关系。
    *   **第一人称模式 (FPS View)**: 模拟 `Local Inspection`，获取高分辨率细节。

### 3.3 待收集线索清单 (Clues as Context Tokens)

你需要在虚拟场景中找到并“点击”以下关键点，系统会将这些视觉信息转化为 **JSON 格式的上下文** 存入 Agent 内存。这一步必须同时满足 **工程逻辑** 和 **AI 推理逻辑**。

#### A 类线索：裂缝形态 (Crack Patterns) -> `Visual_Context`
> *Context 作用: 提供形态学特征，排除温度裂缝（通常在顶层两端）。*

1.  **底层窗角斜裂缝 (Critical)**:
    *   *位置*: 底层东山墙窗户角落。
    *   *视觉特征*: **“倒八字” (Inverted Eight)**，上宽下窄，指向下方中间。
    *   *工程含义 (Engineering Insight)*:
        *   这是一种典型的**剪切破坏**。
        *   当**端部沉降 > 中部沉降**时，墙体产生正弯矩，主拉应力轨迹线呈倒八字分布。
        *   此处暗示东侧地基可能存在湿陷或土体流失。
    *   *Agent 记忆 (Memory Entry)*:
        ```json
        {"type": "crack", "pattern": "inverted-V", "location": "ground_floor_east", "width_trend": "top_wide_bottom_narrow"}
        ```
    *   *推理价值 (Reasoning Value)*: 提供 $\Delta S_{ends} > \Delta S_{center}$ 的几何证据。

2.  **顶部竖向裂缝 (Supporting)**:
    *   *位置*: 顶层窗台下。
    *   *视觉特征*: 竖直向下。
    *   *工程含义 (Engineering Insight)*:
        *   这是**反拱变形**的迹象。
        *   当两端下沉时，结构呈“碟形”变形，顶部窗间墙受压下沉，窗下墙受拉开裂。
    *   *Agent 记忆 (Memory Entry)*:
        ```json
        {"type": "crack", "pattern": "vertical", "location": "top_floor_window", "mechanism": "bending_moment"}
        ```

3.  **纵横墙交接处裂缝 (Supporting)**:
    *   *位置*: 内墙转角。
    *   *工程含义 (Engineering Insight)*: 表明房屋整体性（Integrity）受损，圈梁可能未起到预期的约束作用。
    *   *Agent 记忆 (Memory Entry)*:
        ```json
        {"type": "crack", "pattern": "separation", "location": "internal_corner"}
        ```

#### B 类线索：环境诱因 (Environmental Triggers) -> `Environmental_Context`
> *Context 作用: 提供因果链条中的“因” (Causality Root)。*

1.  **东侧深基坑 (Deep Excavation) [核心证据]**:
    *   *视觉特征*: 距离住宅仅 15m，且无止水帷幕迹象，可见抽水设备。
    *   *工程含义 (Engineering Insight)*:
        *   **基坑降水**会形成降水漏斗，导致周边地下水位下降。
        *   水位下降使土体有效应力增加（$\sigma' = \sigma - u$），引起土体固结沉降。
        *   距离基坑越近，沉降量越大，从而导致**差异沉降**。
    *   *Agent 记忆 (Memory Entry)*:
        ```json
        {"type": "external_factor", "object": "excavation_pit", "distance": "15m", "status": "dewatering"}
        ```
    *   *推理价值 (Reasoning Value)*: **Key Token**。缺失此 Token，Agent 将无法激活 `Settlement by Dewatering` 的推理路径，可能会错误地归因为“地基土湿陷”或“材料老化”。

2.  **散水坡错位 (Confirmation)**:
    *   *视觉特征*: 建筑物四周的混凝土散水坡与主体墙身脱开，且有明显下沉。
    *   *工程含义 (Engineering Insight)*:
        *   这是地基沉降的**直接物理证据**。
        *   证明墙体相对于周边地表发生了位移。
    *   *Agent 记忆 (Memory Entry)*:
        ```json
        {"type": "displacement", "object": "apron", "status": "detached"}
        ```

### 3.4 交互机制与反馈 (Interaction & Feedback)

1.  **感知 (Spotting)**: 准心对准可疑区域 -> 模拟 **Attention Mechanism (注意力机制)** 激活。
2.  **采集 (Collecting)**: 点击鼠标左键 -> 模拟 **Tokenization (词元化)** 与 **Embedding (向量化)** 存入向量数据库。
    *   屏幕左侧 `Agent Memory Log` 实时显示数据流：
        ```json
        [SYSTEM] New Context Added:
        {
          "fact_id": "001",
          "content": "Found Inverted-V cracks at East Wall",
          "embedding_tag": ["structural_damage", "settlement_pattern"]
        }
        ```
3.  **验证 (Verifying)**:
    *   采集正确：`Context Saturation` (上下文饱和度) 上升。
    *   采集错误（如涂鸦）：提示 `Irrelevant Information` (噪声信息)，Agent 会因为信噪比过低而感到困惑。

### 3.5 失败判定 (Failure State: Hallucination Risk)
*   如果进入下一阶段前，**Context 缺失 "Deep Excavation"**，系统会弹出警告：
    > **⚠️ High Hallucination Risk**
    > *Agent 缺少关键环境约束。强行推理可能导致 Agent 编造错误的成因（如“地震”或“施工质量差”）。*
    > *建议：继续 Field Inspection 直到获取环境证据。*

### 3.6 关键思考：LLM 的能力边界 (Critical Thinking: The Boundaries of LLM)

在结束本阶段前，我们需要思考一个核心问题：**仅凭 Phase 1 收集的 Context，Agent 能直接给出鉴定结论吗？**

*   **LLM 的强项 (Capability)**: **模式识别 (Pattern Recognition)**。
    *   它可以根据 `Visual_Context` 识别出“这是倒八字裂缝”。
    *   它可以根据 `Environmental_Context` 推测“基坑可能导致了沉降”。
    *   *结论*: LLM 擅长处理 **定性 (Qualitative)** 描述。

*   **LLM 的弱项 (Limitation)**: **规范判定 (Regulatory Compliance)**。
    *   LLM 无法凭借“直觉”判断 8mm 宽的裂缝是 B 级还是 C 级。
    *   LLM 即使背诵过 JGJ 125，也可能产生“记忆错乱”，混淆不同版本的规范条款。
    *   *结论*: 涉及到 **定量 (Quantitative)** 和 **定级 (Rating)** 的操作，绝不能依赖 LLM 的黑盒推理。

**👉 引出 Phase 2**:
正是因为 Phase 1 只能提供“事实素材”，无法提供“判据”，所以我们必须进入 **Phase 2: 规则注入**。我们需要将 JGJ 125 的刚性条款变成 **可执行的代码逻辑**，强行约束 LLM 的输出。
**记住：在工程领域，Context + Logic = Conclusion。LLM 负责 Context，你（工程师）必须负责 Logic。**

## 4. Phase 2: 大脑规则注入 (Brain Training & Rule Injection)

> **核心理念**: "Neuro-Symbolic AI" (神经符号主义)。
> **你的角色**: 也就是“立法者”。LLM 负责理解语义，你负责制定法律（Rules）。

### 4.1 理论基础：工程规范 vs 模型微调 (Engineering Standards vs Model Fine-Tuning)

在这一阶段，我们实际上是在对通用大模型进行一次 **“轻量级微调” (In-Context Learning / Soft Prompting)**，目的是将 **JGJ 125 规范** 内化为 Agent 的**决策边界**。

*   **工程视角 (Engineering View)**:
    *   规范（如 JGJ 125）是工程界的“法律”，它具有**刚性**和**阈值敏感性**。
    *   例如：裂缝宽度 $w > 10mm$ 是 D 级，而 $w = 9mm$ 可能只是 C 级。这个 $1mm$ 的差距决定了房屋是否需要立即撤离。
*   **AI 视角 (AI Training View)**:
    *   通用 LLM (如 GPT-4) 训练于海量文本，它学到的是**概率分布**。它可能觉得“很大裂缝”通常意味着“危险”，但它对“10mm”这个具体数字没有敬畏感。
    *   **幻觉纠正 (Hallucination Correction)**: 我们需要通过 `System Prompt` 强行覆盖模型的模糊认知，告诉它：“在本任务中，10mm 就是生死线，不允许模糊处理。”

### 4.2 任务：构建判定逻辑树 (Logic Tree Construction)

你需要查阅 **JGJ 125-2016《危险房屋鉴定标准》**，在 Agent 的“大脑控制台”中配置以下两条核心逻辑链。

#### 逻辑链 A：危险性分级 (Quantitative Rating) -> `Classification_Head`
*   **工程目标**: 确定 D 级（整幢危房）的量化指标。
*   **AI 训练目标**: 训练 Agent 的 **分类头 (Classification Head)**，使其能够精确处理数值边界，避免“大概差不多”的模糊输出。
*   **操作**: 填空题。
    *   `IF 承重墙单条裂缝宽度 > [ ? ] mm` (提示: 查阅 JGJ 125 第 4.2.1 条)
    *   `OR 多条平行裂缝宽度 > [ ? ] mm`
    *   `AND 房屋整体倾斜率 > [ ? ] %`
    *   `THEN 危险等级 = D级`
    *   `ELSE IF ... THEN 危险等级 = C级`
*   **参考答案**: `10mm`, `5mm`, `1%`。
*   **训练反馈**: 如果你填了 `20mm`，Agent 的**召回率 (Recall)** 会大幅下降（漏报危房）；如果你填了 `1mm`，**误报率 (False Positive)** 会飙升。

#### 逻辑链 B：成因推断 (Causal Reasoning) -> `Chain-of-Thought`
*   **工程目标**: 区分“地基沉降”与“温度收缩”。
*   **AI 训练目标**: 构建 **思维链 (Chain-of-Thought, CoT)**，强迫 Agent 按照特定的因果路径进行推理，而不是随机联想。
*   **操作**: 逻辑连线。
    *   `Node 1 (Fact)`: Memory 包含 `Pattern: Inverted-V` (倒八字)
    *   `Node 2 (Fact)`: Memory 包含 `Context: Deep Excavation` (深基坑)
    *   `Edge (Logic)`: $\Delta S_{ends} > \Delta S_{center}$ (端部沉降大于中部)
    *   `Output (Conclusion)`: "成因：基坑降水导致端部不均匀沉降"
*   **反例 (幻觉陷阱)**:
    *   如果只连接了 `Node 1` 而忽略了 `Node 2`，Agent 可能会激活错误的路径：`Inverted-V` -> `Top Floor?` -> `Temperature Stress` (这是最常见的温度裂缝误判路径)。

### 4.3 进阶逻辑：时空与冲突 (Advanced Logic: Spatio-Temporal & Conflict)

为了让 Agent 的决策更像资深工程师，我们需要补充两个高阶逻辑模块。

#### 逻辑链 C：稳定性判定 (Temporal Logic) -> `Dynamic Variables`
*   **工程目标**: 决定是“现在修”还是“以后修”。
*   **规则**:
    *   `IF 沉降速率 > 0.05mm/day (连续2个月)`
    *   `THEN 状态 = 活动 (Active) -> 措施 = 加固地基 (Reinforce Foundation)`
    *   `ELSE 状态 = 稳定 (Stable) -> 措施 = 修补裂缝 (Repair Cracks)`
*   **AI 训练点**: 训练 Agent 理解 **动态变量**。如果忽略时间维度，Agent 可能会建议对活动裂缝进行表面修补，这在工程上是无效且浪费资金的。
*   **实训操作 (Training Action)**: **时间轴推演**。
    *   系统展示一张 [时间-裂缝宽度] 折线图，显示速率为 `0.08mm/day`。
    *   Agent 询问：“建议立即灌浆修补？”
    *   **你的操作**: 点击 `Reject (驳回)` 并标注 `Reason: Still Active`。
    *   *反馈*: 如果你批准了，系统会模拟“30天后修补处再次开裂”，任务失败。

#### 逻辑链 D：冲突仲裁 (Arbitration Logic) -> `Safety Bias`
*   **工程目标**: 处理相互矛盾的指标（如裂缝很小，但倾斜很大）。
*   **规则**: **木桶效应 (Worst-case Principle)**。
    *   `Final_Rating = Max(Crack_Rating, Tilt_Rating, Foundation_Rating)`
*   **AI 训练点**: 纠正 LLM 的 **平均化偏见 (Averaging Bias)**。
    *   *错误思维*: "裂缝是A级，倾斜是D级，综合来看算 C级吧？"
    *   *正确思维*: "只要有一个指标是 D级，整体就是 D级。" 我们需要通过 `Logit Bias` 或 `System Prompt` 强化这种“安全第一”的权重。
*   **实训操作 (Training Action)**: **权重博弈**。
    *   场景: 裂缝 `2mm` (安全), 倾斜 `1.2%` (极危险)。
    *   **你的操作**: 调整 **Safety Weight (安全权重)** 滑块，从 `Balanced (平衡)` 拉向 `Conservative (保守)`。
    *   *结果*: Agent 的决策从“建议观察”变为“立即撤离”。

### 4.4 验证与调试 (Unit Testing & Alignment)

配置完成后，系统会生成 3 个虚拟案例进行**单元测试 (Unit Test)**，以验证 Agent 的**对齐度 (Alignment)**：

1.  **Case A (边界测试 - Boundary Value Analysis)**:
    *   *输入*: 裂缝 9.8mm，倾斜 0.9%。
    *   *工程预期*: **非 D级** (接近但未超标)。
    *   *AI 行为*: 必须抑制输出“危险”的冲动，严格遵守 `< 10mm` 的约束。
2.  **Case B (幻觉测试 - Anti-Hallucination)**:
    *   *输入*: 裂缝 2mm，但出现在顶层两端。
    *   *工程预期*: **温度裂缝**。
    *   *AI 行为*: 识别出 `Pattern: Inverted-V` 出现在顶层是不符合沉降逻辑的（沉降裂缝通常在底层），从而**拒绝**归因为地基沉降。

## 5. Phase 3: 智能工具挂载 (IoT Tool Crafting & Function Calling)

> **核心理念**: "Embodied AI" (具身智能)。
> **你的角色**: "Hardware Interface Engineer" (硬件接口工程师)。你需要为 Agent 装备“感知外设”。

### 5.1 理论基础：三维融合 (Theoretical Basis: The Trinity)

本阶段的实训不仅仅是学习“如何使用工具”，而是要理解 **工程 (Engineering)**、**人工智能 (Agent)** 与 **物联网 (IoT)** 三者如何深度融合，构建下一代监测体系。

#### 1. 工程视角：从点状测量到连续监测 (From Spot Check to Monitoring)
*   **传统痛点**: 传统的工程鉴定是“点状”的（如：工程师每月去现场测一次）。这种方式极易漏掉关键的**瞬时峰值**（如：暴雨当天的沉降突变）。
*   **IoT 变革**: IoT 设备提供了高频、连续的**时间序列数据 (Time-Series Data)**。它让我们从关注“此刻的状态”转变为关注“变化的速率与趋势”，这对于判定结构稳定性（JGJ 8 规范）至关重要。

#### 2. Agent 视角：从大脑到具身 (From Brain to Embodied AI)
*   **缺失的拼图**: 前两个阶段的 Agent 只是一个“缸中之脑”，它有逻辑但没有感知。
*   **Function Calling**: 通过将 IoT 设备封装为 API（如 `get_crack_width()`），我们实际上是在为 Agent 赋予**感官 (Senses)**。这使得 Agent 能够主动地去“看”、去“测”，从而实现 **Perception-Action Loop (感知-决策闭环)**。

#### 3. IoT 视角：从数据到信度 (From Data to Trust)
*   **数据脏乱差**: 真实世界的传感器数据充满了**噪声 (Noise)**、**漂移 (Drift)** 和 **异常值 (Outliers)**。
*   **边缘计算 (Edge Computing)**: 我们不能把原始垃圾数据直接喂给 LLM（这会导致幻觉）。必须在设备端或网关层进行**数据清洗 (Data Cleaning)**（如卡尔曼滤波、温度补偿），确保 Agent 接收到的是**高置信度 (High-Fidelity)** 的事实。

### 5.2 任务：AIoT 系统构建 (Building the AIoT System)

你需要按照 **物理布设 -> 逻辑配置 -> 数据治理** 的顺序，完成传感器的部署。

#### 任务 1: 物理布设 (Physical Deployment) - 工程视角
> *目标: 确保数据来源的有效性。*
*   **挑战**: 传感器不是随便贴的，必须贴在**受力关键点**。
*   **操作**: 拖拽 `Smart Crack Sticker` 到 3D 模型的墙面上。
    *   **位置 A**: 裂缝最宽处（中部）。
    *   **位置 B**: 裂缝尖端（延伸处）。
    *   **位置 C**: 完好墙面（对照组）。

## 6. Phase 4: SOP 编排 (SOP Planning & Workflow Design)

> **核心理念**: "Chain of Thought" (思维链) -> "Graph of Operations" (操作图谱)。
> **你的角色**: "System Architect" (系统架构师)。你需要将前三阶段的成果串联成一个自动运行的闭环。

### 6.1 任务：绘制自动化监测流程图 (Workflow Graphing)

SOP 是一个**装配车间**，它必须显式调用前三个阶段生产的“零件”。如果缺少任何一个前置模块，工作流就会中断。

#### 1. 依赖关系图谱 (Dependency Mapping)
*   **节点 A: 获取环境上下文 (Get Context)**
    *   *依赖*: **Phase 1 (Memory)**。
    *   *说明*: 调用存储在向量数据库中的“深基坑”和“倒八字裂缝”信息。
    *   *Risk*: 若 Phase 1 未采集“深基坑”，此节点输出为空，导致后续成因分析失败。
*   **节点 B: 获取实时数据 (Get Real-time Data)**
    *   *依赖*: **Phase 3 (IoT Tools)**。
    *   *说明*: 调用 `Smart Crack Sticker` 的 API。
    *   *Risk*: 若 Phase 3 未开启“卡尔曼滤波”，此节点输出噪声数据，导致误报。
*   **节点 C: 执行判定规则 (Execute Rules)**
    *   *依赖*: **Phase 2 (Brain Logic)**。
    *   *说明*: 加载 `JGJ 125 Logic Tree` 进行评级。
    *   *Risk*: 若 Phase 2 规则设置错误（如阈值设为 20mm），此节点将输出错误的 D 级判定。

#### 2. 节点连线与逻辑编排 (Node Linking)
你需要在一个类似 ComfyUI 的可视化界面中，拖拽上述节点并连线。

*   **Trigger (触发器)**: `Cron Job (定时任务)`
*   **Action (动作)**: `Call Tool: get_crack_width`, `Call Tool: get_tilt_angle`
*   **Logic (逻辑)**: `Rule Engine (Phase 2)`, `Cross-Check (交叉验证)`
*   **Output (输出)**: `Generate Report`, `Send Alert`

#### 挑战 A：线性思维陷阱 (The Linear Trap)
*   **错误连线**: `Cron Job` -> `Get Crack Width` -> `Generate Report`。
*   **后果**: 如果传感器因网络波动返回 `0.00mm`，系统会立即生成“房屋安全”的错误报告，掩盖真实风险。
*   **正确连线**: `Cron Job` -> `Get Crack Width` -> **`Data Validator (数据校验)`** -> `Rule Engine`。
    *   *校验规则*: `IF val == 0 OR val == null THEN Retry(3)`。

#### 挑战 B：多源验证 (Multi-Source Verification)
*   **错误连线**: 仅依赖裂缝数据定级。
*   **后果**: 单一指标容易误判（例如裂缝只是表层粉刷层开裂，结构并未受损）。
*   **正确连线**:
    *   并行执行: `Get Crack Width` AND `Get Tilt Angle` (同时获取倾斜数据)。
    *   汇聚节点: **`Logic: Safety Bias`** (Phase 2 定义的仲裁逻辑)。
    *   *逻辑*: 只有当“裂缝 > 10mm”且“倾斜 > 1%”同时满足（或任一满足，取决于你的仲裁设定）时，才触发红色警报。

### 6.2 实训操作：Debug 你的 SOP (Debug Your SOP)

编排完成后，点击 `Simulate Run` (模拟运行)，系统会注入突发事件：

1.  **事件**: “传感器 Crack_001 掉线，返回 null。”
    *   *预期行为*: Agent 触发 `Retry` 机制，如果 3 次失败，发送“设备故障工单”，而不是“房屋安全报告”。
2.  **事件**: “裂缝宽度激增至 12mm，但倾斜率仅 0.1%。”
    *   *预期行为*: Agent 识别数据冲突，调用 `Reasoning: Anomaly Check`，推测可能是“传感器脱落”或“局部破坏”，建议人工复核，而不是直接下达撤离指令。

## 7. Phase 5: 实战验收 (Execution & Final Review)

> **核心理念**: "Human-in-the-loop Evaluation" (人机协同评估)。
> **你的角色**: "Chief Engineer" (总工程师)。审查 Agent 提交的最终报告。

### 7.1 任务：全自动运行与报告生成 (Auto-Run)

点击 `Execute SOP`，观看 Agent 实时处理数据流：
1.  **Context Loading**: "Loaded 2 environmental factors."
2.  **Sensing**: "Sensor_01 returns 12.5mm (Filtered)."
3.  **Reasoning**: "Rule A triggered (Width > 10mm). Rule D triggered (Safety Bias)."
4.  **Drafting**: "Generating Report..."

### 7.2 成果物：房屋危险性鉴定报告 (The Deliverable)

Agent 将输出一份结构化的 PDF 报告。你需要检查以下关键点：

#### 关键点 1: 结论准确性 (Conclusion)
*   **正确**: **D级 (整幢危房)**。
*   **错误**: C级 (局部危房)。
    *   *原因*: 可能是 Phase 2 的“木桶效应”逻辑未开启，导致 Agent 忽略了倾斜指标。

#### 关键点 2: 成因分析 (Root Cause)
*   **正确**: "邻近基坑降水导致端部地基不均匀沉降"。
*   **错误**: "地基土湿陷" 或 "材料老化"。
    *   *原因*: Phase 1 漏采了“深基坑”线索，导致 Context 缺失。

#### 关键点 3: 处置建议 (Recommendations)
*   **正确**: "立即停止基坑施工，临时支撑，人员撤离"。
*   **错误**: "灌浆修补裂缝"。
    *   *原因*: Phase 2 的“稳定性判定 (Temporal Logic)”失效，Agent 未识别出裂缝仍处于**活动期 (Active)**，错误的修补建议可能导致安全事故。

### 7.3 最终评分 (Scoring)

系统将根据报告质量给出 S/A/B/C/D 评级：
*   **S级**: 所有关键点正确，且数据经过滤波处理，逻辑链完整。
*   **C级**: 结论正确但成因分析错误（“蒙对了”）。
*   **Fail**: 结论错误（漏判危房），或建议违规（对活动裂缝灌浆）。
